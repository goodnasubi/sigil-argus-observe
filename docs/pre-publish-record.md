## 2. G2 関門 検証記録

ADR 0020 決定 1〜4、および ADR 0067 決定 1〜7 に基づき、各設計決定の適合状況を以下に記録する。

### 2.1 決定 1: 責務と配置
- **三位一体の監視核**: ログ・メトリクス・死活監視を単一の契約体系で統合。
- **配置**: 出力ライブラリ（`argus_observe.sigil`）は各 Sigil サービスへ組み込み、受信ポート（`argus_receive.sigil`）および永続化アダプタ（`argus_collect.sigil`）は独立デーモンとして `sigil-orchestra` と連携。

### 2.2 決定 2: ログ出力の仕様
- **形式**: 1 行 1 レコードの NDJSON 形式。末尾 LF を含め最大 65,536 バイト。
- **切り詰め**: 上限超過時は JSON エスケープ後のバイト数に合わせて UTF-8 文字境界で切り詰め、`"truncated":true` を付与。
- **タイムスタンプ**: UTC ISO 8601（ミリ秒またはマイクロ秒精度 `Z`）。
- **命名規則**: component は `[a-z]+(-[a-z]+)*`。

### 2.3 決定 3: メトリクス出力の仕様
- **種類**: Counter、Gauge、Histogram。
- **初期化と採番**: ゼロ値初期化、`snapshot` による同一時刻採番。
- **命名規則**: 単位サフィックス（`_total`, `_bytes`, `_seconds` 等）。
- **カーディナリティ防御**: ラベル数上限は 10 個（利用側最大 9 個、ヒストグラムは `le` を含め最大 8 個）。高カーディナリティ値（ユーザー ID、生 URL、時刻等）の排除。

### 2.4 決定 4: 死活監視の仕様
- **プル型**: `Probe.Http`（`GET /healthz` 2xx）および `Probe.Tcp`（接続成否）。3 連続失敗で `Dead`、成功時に `Healthy` に復旧。
- **プッシュ型**: `heartbeat_ping` によるハートビート受信。最終受信から 30 秒で `Dead`、再受信で `Healthy` に復旧。

### 2.5 決定 5: 永続化アダプタ
- **sigil-db 核連携**: 直列 WAL トランザクションによるアトミックなバッチ確定（`flush`）。
- **索引**: ログは追記 ID・時刻・component ハッシュ・level。メトリクスは component・name・ts・labels ハッシュによる一意キー。
- **クラッシュ復旧**: 再起動時の WAL リプレイによる完全整合性復元。

### 2.6 決定 6: ダッシュボード連携とクエリ API
- **HTTP JSON クエリ**:
  - `/api/logs`: component, level, since, until, prefix, limit による直近ログ降順取得。
  - `/api/metrics`: 件数、合計、最小、最大、最新値の集約。走査上限到達時は `complete: false`。
  - `/api/components`: 死活監視状態一覧（healthy / degraded / dead）。

### 2.7 決定 7: 第4段（データ保持・流量制御・負荷境界）
- **容量上限と FIFO ローテーション**: ディスク容量上限（既定 10 GB）到達時、稼働継続を最優先して古いログから FIFO で自動破棄（`prune_oldest_logs`）。
- **保持期限**: 保持期間（既定 7 日）超過ログの自動削除（`prune_expired_logs`）。
- **流量制御（レートリミット）**: 1 秒窓の最大受信数（既定 10,000 件/秒）超過時、HTTP は `429 Too Many Requests`（`{"error":"rate_limited"}`）、生 TCP は `ERR rate_limited\n` を返却し、次窓で自動回復。
- **負荷境界防御**: `scan_limit` による走査打ち切り、`query_max` によるクランプ、413 Payload Too Large、431 Request Header Fields Too Large、64 KB 超過行の切断。

### 2.8 ADR 0020 決定 1: 定数時間の検査
- トークン・暗号鍵の照合は本監視受信口には存在しないが、component ハッシュやラベルハッシュ比較におけるタイミングリークの懸念がないことを確認。

### 2.9 ADR 0020 決定 2: ファジング
- `argus_accept_test.sigil` による異常 JSON、過大行、不正タイムスタンプ、不正 component、不正ラベル等の境界入力に対するパニック不在・型付きエラー検証。
- 実ソケット経由での変異リクエスト（過大ヘッダー、過大本文、過大生 TCP 行、不正メソッド）に対する適切なステータスコード返却とプロセス健全性確認。

### 2.10 ADR 0020 決定 4: サプライチェーン
- 外部依存クレートを追加せず、JSON パーサーを含め Sigil 標準ライブラリおよび `sigil-db` 核（commit `9483e36`）のみを使用。

### 2.11 秘密情報の不在確認
- `git log -p` およびリポジトリ内の全ファイル走査により、秘密鍵、API トークン、認証パスワード等の秘密情報が含まれていないことを確認済み。
- ログ本文のエスケープ・サニタイズ処理により、バイナリ混入やフォーマット破壊を防止。

## 3. 負荷・境界試験の記録（Stage 4）

### 3.1 試験構成
- **環境**: Linux x86_64（Ubuntu 24.04.5 LTS / remote VM）
- **コンパイラ**: Sigil（commit `60cc4f9acf2e7c7a69cec1c60af5e2e4515ac71a`）
- **データベース核**: `sigil-db`（commit `9483e36f08c35bfc62b3beeb008a531887506037`）
- **試験項目**:
  1. ディスク容量上限到達時の FIFO ローテーション破棄試験（古いログの自動破棄と稼働継続）
  2. 保持期間超過ログの自動削除試験（モック時計を用いた期限切れ判定と残存データの整合性）
  3. 高頻度ログ流入時の HTTP 流量制御試験（429 Too Many Requests 拒否と次窓での回復）
  4. 高頻度ログ流入時の生 TCP 流量制御試験（ERR rate_limited 応答と次窓での回復）
  5. 負荷境界試験（メトリクス走査上限 complete:false、クエリ上限クランプ、413、431、64 KB 超過行切断）

### 3.2 実施結果まとめ

| 試験項目 | 検証シナリオ / 条件 | 期待動作 | 結果 |
|---|---|---|---|
| **容量超過 FIFO ローテーション** | 容量上限（400 バイト）に対し 4 件のログ（計 489 バイト）を順次投入 | 最古のログ（log 1）が自動破棄され、最新のログ（log 4）が保持され稼働が継続すること | 合格 (Pass) |
| **保持期間超過削除** | 保持期間（5,000 ms）に対し 10 秒前のログと現在ログを投入 | 保持期間を超過した古いログのみが削除され、新しいログのみが照会可能であること | 合格 (Pass) |
| **HTTP 流量制御** | 流量上限 3 件/秒に対し、同一秒窓内で 4 件目のログを投入 | 4 件目が 429 Too Many Requests（`{"error":"rate_limited"}`）で拒否され、時計を 1 秒進めた次窓で再び受理されること | 合格 (Pass) |
| **生 TCP 流量制御** | 流量上限 2 件/秒に対し、同一秒窓内で 3 件目のログ行を送信 | 3 件目が `ERR rate_limited\n` で拒絶され、時計を 1 秒進めた次窓で `OK\n` に復旧すること | 合格 (Pass) |
| **メトリクス走査上限** | 6 件のメトリクス標本に対し走査上限 `scan_limit = 4` で `/api/metrics` 照会 | `complete: false` および `scanned: 4` が返却され、過大負荷時の走査が安全に打ち切られること | 合格 (Pass) |
| **クエリ上限クランプ** | 6 件のログに対し `limit = 1000` で照会（`query_max = 3` 設定） | 上限値 3 件にクランプされて結果が返却されること | 合格 (Pass) |
| **本文上限超過** | `max_body_bytes = 2000` に対し 2,500 バイトの POST 本文を送信 | 413 Payload Too Large で拒否されること | 合格 (Pass) |
| **ヘッダー上限超過** | 8 KB 超過（約 9 KB）の HTTP 要求ヘッダーを送信 | 431 Request Header Fields Too Large で拒絶されること | 合格 (Pass) |
| **生 TCP 1 行 64 KB 超過** | 64 KB 超過（約 66 KB）の 1 行 NDJSON を生 TCP 送信 | `ERR line_too_large\n` 応答後に接続が切断されること | 合格 (Pass) |
| **評価器・ネイティブ整合** | `tests/check_stage4.py` を評価器（`sigil run`）およびネイティブ（`sigil build`）で実行 | 全シナリオが両実行モードで同一結果（コード 0）で通過すること | 合格 (Pass) |

## 4. G3 で所有者へ提示する確認項目

ADR 0020 決定 3 に従い、外部公開を判断する G3 関門において所有者（goodnasubi）へ提示・確認を求める項目を以下に列挙する。

### 1. 単一ノード限定と可用性設計（決定 1、決定 7）
- **内容**: 初版は単一ノード（単一プロセス・単一 `sigil-db` インスタンス）限定の設計であり、複数ノード間のログ分散集約やレプリケーションは含まない。
- **確認事項**: 集約サーバー自身の冗長化が必要な場合は、インフラ層でのプロセス監視・自動再起動（systemd、コンテナオーケストレータ等）および共有ストレージや定期バックアップ運用を前提とすることの確認。

### 2. データ破棄の許容と稼働継続優先設計（決定 7、適合の限界）
- **内容**: ADR 0067「適合の限界」に基づき、ディスク容量上限到達時および高頻度流入時は「監視機能自体の停止やディスク枯渇によるプロセス死」を回避するため、最古ログの FIFO 破棄およびレートリミットによる流入拒否（429 / ERR rate_limited）を行う。
- **確認事項**: 監視サービスとしての稼働継続性をデータ完全保持よりも優先する方針、およびデータ完全性を要求する監査ログ等には専用の監査機構を用いることの確認。

### 3. 全文検索の非提供と検索境界（決定 6、決定 7）
- **内容**: 全期間の全文検索やインデックスは提供せず、直近ログの `prefix` 前方一致検索および時間・component・level 範囲検索に限定する。
- **確認事項**: 大規模・長期の全文分析は外部ログ基盤（必要に応じたエクスポート連携）に委ねる方針であることの確認。

### 4. 外部網接続時の暗号化と認証（決定 7）
- **内容**: 本プロトコルは内部網向けの平文 HTTP/生 TCP プロトコルであり、トランスポート層での暗号化（TLS）や認証機構は内蔵されていない。
- **確認事項**: 既定のループバック（`127.0.0.1`）から外部ネットワークへ接続を公開する場合、TLS 終端プロキシ（`sigil-shield-tls` や VPN/mTLS）およびネットワーク分離（VPC、内部専用サブネット）の設置が必須であることの確認。

### 5. 外部公開可否の最終決定
- **結論**: **G2 は外部公開を承認しない**。本検証記録および次期 G3 レビュー結果に基づき、所有者（goodnasubi）が外部公開の可否を最終決定する。
